Python is a plugin-level setting on Windows, and the plugin detects it by itself. The first settings page gets a **Python executable** field and a **Python status** row: the name or path that answered and the interpreter it runs when found, otherwise a warning with a python.org download button and the `winget` command, plus a recheck button. Detection tries the configured value, then `python`, `python3`, `py -3`; it recognizes the Microsoft Store placeholder and resolves every candidate to its `sys.executable`, so launchers and shims (Python 3.14's install manager ships one) never become the spawn target. Nothing is written back: the field holds only what you type, and a profile's Python field keeps its portable value (`python3` stays `python3`), so settings synced to macOS or Linux keep working. Profiles inherit the setting unless their own Python field is set. Stored backends follow each profile's effective Python result: a working profile override keeps ConPTY even when plugin-level discovery fails. Without a usable Python, ConPTY profiles switch to ConHost and are marked automatic; once that profile has usable Python, exactly those switch back, and a detection that merely timed out changes nothing. A ConPTY host that starts but never becomes ready trips a session-wide breaker (later terminals open on ConHost with one notice; reloading tries again), while a shell Windows cannot find or start does not. ConHost with a Python that lacks `psutil`/`pywinctl` opens without its resizer, and the profile editor offers a copy button with the exact `pip install` command for that interpreter. Addresses the exit-code-9009 and "no Python found" reports in [GH#77](https://github.com/polyipseity/obsidian-terminal/issues/77), [GH#79](https://github.com/polyipseity/obsidian-terminal/issues/79), [GH#115](https://github.com/polyipseity/obsidian-terminal/issues/115), and [GH#153](https://github.com/polyipseity/obsidian-terminal/issues/153).
